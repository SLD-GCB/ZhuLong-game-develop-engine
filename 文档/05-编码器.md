# 编码器

`编码器/` 是这套东西的前端，在**项目根目录**。它不是场景编辑器，是一个**代码编辑器** ——
因为在这个项目里，游戏不是配置出来的，是**写**出来的。场景是数据（`.scene`），程序是代码
（`.py` / `.cpp`），而编码器是写这两样的地方。

两种开法：

```bat
:: 从源码跑（要这个解释器里有 PySide6）
python 编码器\main.py

:: 拿到包的人：双击包里的 烛龙.exe
```

**包里没有启动脚本** —— 双击 `烛龙.exe` 就是全部。那个 exe 自带 PySide6，不需要解释器。

不用设 `PYTHONPATH`：`runtime.py` 自己会找 `zlong`（先看 `运行环境/`，再看 `build/**/`）。后端
没构建过的话，状态栏右下角会写着"后端未构建"。

## 窗口

**两页**：写代码的那一页，和 3D 建模那一页。工具栏最左边那两个开关切它们。

```
┌─ 工具栏 ──────────────────────────────────────────────────────────────────┐
│ [代码][3D 建模] │ 新建 打开 保存 │ 运行 停止 │ 语言 [Python▾] │ 参数 [____] │
├──────────┬───────────────────────────────┬────────────────────────────────┤
│ 文件树    │ 查找/替换条（Ctrl+F 才出现）    │ 画面                            │
│          ├───────────────────────────────┤  ← 运行出来的东西在这里           │
│          │ 标签页 + 代码                  │  1024×640 · 第 71 帧            │
│          │                               │                                │
├──────────┴───────────────────────────────┴────────────────────────────────┤
│ 输出（控制台）：编译输出、脚本输出、可点的 traceback                        │
└──────────────────────────────────────────────────────────────────────────┘
```

左边文件树、中间代码、右边画面、底下控制台。三个分隔条都能拖。底下那个控制台**两页共用** ——
建模器说的话（"面 1 / 共 6 个"、"移动完成…"）也落在那里，所以边建模边看得见。

## 3D 建模页

工具栏上按「3D 建模」就进去了：

```
┌─ 工具栏 ──────────────────────────────────────────────────────────────────┐
│ [代码][3D 建模] │ 新建 打开 保存 │ 运行 停止 │ ……                          │
├───────────────────────────────────────────────────────────────────────────┤
│ [选面][选点][撤销]                                        [开始建模]       │
├───────────────────────────────────────────────────────────────────────────┤
│                                                                           │
│                        （建模器画出来的东西）                               │
│                                                                           │
│ 右键转 · 中键平移 · 滚轮缩 · 左键选一个点或面，按住就拖着走   800×500 · 第 9 帧│
├───────────────────────────────────────────────────────────────────────────┤
│ 输出（控制台）                                                             │
└───────────────────────────────────────────────────────────────────────────┘
```

进去的时候它会**顺手把建模器起起来**（如果还没有东西在跑），所以进去就是能用的。要是已经有东西
在跑，它不抢 —— 悄悄把别人踩掉是最难查的那种意外；想换就自己按「开始建模」。

建模器自己的操作写在 [04-宿主](04-宿主.md) 的 `modeler` 那一行：`1`/`2` 选面选点、`E` 挤出、
`D` 细分、`B` 切角、`C` 硬边、`X` 删面、`Z` 撤销，鼠标右键转、中键平移、滚轮缩、左键选一个拖着
走。**挤出、细分和切角是加面，删面是唯一一个减面的**；在那之前每一次编辑都只是把点挪个位置，点的
个数和面的个数从来没变过。`C` 不改拓扑，它标的是**硬边**：那条边的两头这一圈细分时不会跟着变圆
（`B` 切角的时候硬边也跟着收，不会一声不响地丢掉；`X` 删面同理）。

**那一页上的按钮不自己实现任何东西，它们只替用户敲一下键**：

| 按钮 | 敲的是 | 就是 `宿主/modeler` 里的 |
|---|---|---|
| 选面 | `K 49 1` | 键 `1` |
| 选点 | `K 50 1` | 键 `2` |
| 挤出 | `K 69 1` | 键 `E` —— 把选中的面沿它自己的法线挤出一层 |
| 细分 | `K 68 1` | 键 `D` —— Catmull-Clark 细分一次，整个模型 |
| 切角 | `K 66 1` | 键 `B` —— 点模式切那个点，面模式切那个面的四个角 |
| 硬边 | `K 67 1` | 键 `C` —— 把选中那个面的一圈边标成硬边 / 取消 |
| 删面 | `K 88 1` | 键 `X` —— 删掉选中的面，在那儿留一个洞 |
| 撤销 | `K 90 1` | 键 `Z` |

「上色」不敲键，它发的是**颜色**：`A <R> <G> <B> <A>`，四个 0..1 的数。按下去弹一个取色框，挑完在
控制台里能看到 `面 3 换成材质 1（0.90, 0.10, 0.10），模型现在有 2 种`。**同一个颜色会复用同一个材质
槽** —— 涂十次同一个红不会长出十种材质。模型是按材质拆开画的，所以"有几种颜色"就是"几个可画节点"。

「贴图…」发的是一条路径（`T <路径>`），挑一张 **BMP**。要注意的是它挂的是**那种材质**，不是那一个面
—— 材质是好几个面共用的，所以给一个面上贴图常常会同时给另外几个面也贴上。图的路径**尽量存成相对这
份模型的**：图就在模型旁边的时候，那份模型连图一起挪走还能用；不在旁边就存绝对路径，能用，但换台机器
就找不着了，控制台会说出来。

### 模型的存和读

「打开…」「导入…」和「保存」是**例外**：它们发的不是键，是路径。键盘那套送不了一个字符串，所以协议
里另有 `S <路径>` / `L <路径>` / `I <路径>` 三行，路径是整行剩下的全部。按「保存」时如果还没存过，
会先问存到哪儿；之后就一直是那个地方了，按 `S` 也是存回那里。进这一页的时候会把上次那个模型直接读
进来。

- **「打开…」** 读一个 `.model` —— 自己的模型，存读的格式见 [03-引擎](03-引擎.md)。
- **「导入…」** 读一个 `.obj` —— **别人的网格文件**。它一定是有损的（五个角以上的面扇成三角形、没
  被用到的点丢掉、法线不用），所以控制台会把账报出来：`点 4 → 3（1 个没被面用到，丢了）`。
- **「保存」不会写回一个导入的文件。** 导进来之后"手上这份从哪儿来"就清掉了，按保存会先问存到哪儿
  —— 那正好是"我的模型"和"借来的文件"该有的区别。想留下就另存一个。

**为什么路径不能当命令行参数传**：Windows 把命令行按 ANSI 代码页交给 C 运行库，`--model 中文路径`
**还没进 `main`** 就已经不是原来那串字节了（这是量出来的，不是推测）。stdin 上那串是 UTF-8 的字节，
原样到得了。所以建模器**不收 `--model`**，路径只从管子里来。

（`--width` / `--height` / `--shadow` 照旧收 —— 它们的值是 ASCII。）

所以这一页和"打开 `宿主/modeler/main.cpp` 按 F5，然后用鼠标键盘操作它"是**同一条路**，只是排得
顺手一点。协议就是 [鼠标](#鼠标) 那一节那张表 —— 建模器把收到的键当键盘，别的一个字都不用知道。
按完按钮焦点会还给画面，否则下一个键跑进编辑器里，按了一下「撤销」再想撤销一次就落空了。

**建模器从哪来**：包里是 `建模器/建模器.exe`（打包时装好的成品，见 [07-打包与发布](07-打包与发布.md)），
源码树里是 `build-zig\宿主\zlong_modeler.exe`。两个地方按顺序找，都找不到就在控制台里把找过的路径
原样列出来，而不是起一个空的东西。

**它为什么值得单独一页**：写代码那一页是「文件树 + 代码 + 画面」三栏，而建模要的是一块尽量大的
画面和一条工具，两边需要的布局不一样。共用的是底下那个控制台和那套跑程序的机制 ——
[04-宿主](04-宿主.md) 里 `modeler` 那一行。**键位、鼠标、每一个操作怎么用，见
[10-3D建模器](10-3D建模器.md)。**

**画面按面板的形状出，不是拿一个固定的尺寸去塞。** 起建模器的时候，编辑器读一下面板的可画
区域，把那个宽高当 `--width` / `--height` 交给它。固定的后果是两边留黑边：面板越宽，黑边
越宽，看上去就是「这块画面很小，没铺满」。

而**像素总数保持建模器自己那个 800×500 的份量** —— 那一套默认值是量着帧率挑的（800×500
是 54 帧档，1024×640 掉到 34 帧），照面板原样出图在宽屏上会多出一倍多的像素。所以这里只
换形状、不涨份量：图铺满，帧率不动。自己在参数框里写了 `--width` / `--height` 的，一个字
都不加。

## 编辑

| 动作 | 快捷键 | 说明 |
|---|---|---|
| 撤销 / 重做 | `Ctrl+Z` / `Ctrl+Y` | |
| 剪切 / 复制 / 粘贴 | 常规 | 只作用于编辑器，不碰画面面板 |
| **注释** | `Ctrl+/` | 符号跟着**语言**走（`#` 或 `//`）；整块按**最浅那行**的列对齐，所以块的形状不变 |
| 复制行 | `Ctrl+D` | 光标落到副本上 |
| 上移 / 下移行 | `Alt+↑` / `Alt+↓` | 到顶/到底就不动（最后那个空行不算一行） |
| 转到行 | `Ctrl+G` | 行号超了会落到最后一行 |
| 放大 / 缩小 / 复位字号 | `Ctrl+=` / `Ctrl+-` / `Ctrl+0` | 所有标签一起改，会记住 |
| 查找 / 替换 | `Ctrl+F` / `Ctrl+H` | 见下 |
| 查找下一个 / 上一个 | `F3` / `Shift+F3` | |
| 运行 / 停止 | `F5` / `Shift+F5` | 见下 |

编辑器自己会的（不用按键）：

- **回车**跟着上一行的缩进；上一行以 `:` 或 `{` 结尾就再缩一级
- **Tab** 到下一个档位（4 格）；选中多行时整块缩进，`Shift+Tab` 缩回去
- **括号引号自动成对**；下一个位置已经是配对的闭符号时，打它只是**跨过去**，不会多一个
- **退格**在空括号中间把两边一起删掉
- 光标旁边的括号和它的另一半会一起亮
- 行号栏、当前行底色

**没做的**：不能折叠、没有补全、没有跳转到定义。它是个编辑器，不是 IDE。

## 查找替换

`Ctrl+F`（`Ctrl+H` 带替换）在代码上方压出一条横条，不是弹窗 —— 弹窗会抢焦点，横条是编辑器的一
部分。

- 上一个 / 下一个 / 循环回绕
- 三个开关：`Aa` 区分大小写、`词` 全字、`.*` 正则
- 命中计数 `3/17`；**所有**命中的位置在代码里高亮，不只当前那个
- 替换里有 `\1` 到 `\9` 的捕获组（Qt 的 `QTextDocument` 搜索不替你做这件事，是这里自己做的）
- Esc 关掉，焦点回到代码

两件容易踩的：

- **普通查找是字面量**，不是正则 —— `.` 就是一个点。要正则得勾 `.*`。
- Qt 的搜索**按 flag 判大小写，不看正则自己的选项**。一个不带 flag 的区分大小写正则会匹配到
  小写。所以大小写是当 flag 传的。

## 语言下拉框

工具栏上那个 `语言 [Python▾]`。**一个文件是什么语言，只决定三件事**：怎么上色、注释用什么符号、
按 F5 走哪条路。

打开文件时按后缀自动选（`.py` / `.cpp` / `.h` / `.txt`…），你可以随时改。改了只影响**当前标签**。
第三个选项是 `纯文本` —— 不加上它，一个 `.txt` 打开时只能显示 Python 或 C++，那是假的。

**新建**跟着下拉框走：选 C++ 时新建出来的是 `untitled.cpp`。

> **一条已经坏掉的旧承诺**：MSVC 时代，编辑器会给编译器传 `/Tp`（强制按 C++ 处理，不看你写的是
> 什么后缀），所以 `.txt` 里写的 C++ 也编得动，下拉框说"这是 C++"，编译器就得当它是 C++。
> 换成 Zig 之后这一条**没有接上** —— `zig c++` 按后缀判语言，`试.txt` 会被当成目标文件丢给
> 链接器，报 `lld-link: error: 试.txt: unknown file type`。
>
> 所以现在：**语言选 C++，后缀也必须是 `.cpp` / `.cc` / `.cxx`。** Python 那一面不受影响（走
> 哪条路由编辑器自己定，和编译器无关）。要补回这一条，是在编译命令行里加 `-x c++`。

## 运行

### Python 那一面

按 F5，编辑器启动的不是你的脚本，是一个**宿主程序**，把脚本交给它。它做两件事：

**一、把 stderr 变成画面通道。** 你的脚本自己的 stderr 被指到 stdout，所以 traceback 和 warning
照旧进控制台，只有帧走另一条路。

**二、顶替 `zlong.System`**，换成一个"永远有宿主"的版本。没有宿主的机器照样渲染（只是谁也不
给），所以脚本不写 `set_platform` 的话画面哪儿都去不了；换掉之后就有了。

关键：**脚本自己指定了宿主也不会丢**。编辑器把自己那半包在外面 —— 先显示这一帧，再转交给脚本
指定的宿主。所以 `scene_demo.py` 的 PNG 照样写出来，同时右边的面板也拿到了画面。

脚本还是普通脚本：`import zlong`，建场景，`machine.load(scene)`，`machine.run(300)`。
它甚至可以不碰 zlong（纯 Python 脚本照跑）。

**那个宿主程序在哪**：源码树里是 `编码器/live.py`；包里它在
`运行环境/python/harness/live.py`（`frames.py` 也在那儿）—— 它是**机器的一部分**，不是产品的
一部分，所以不摆在产品目录里。它必须是一个**文件**：冻结在 exe 里的东西，子进程读不到。

### C++ 那一面

按 F5 → 编译 → 运行。编译器是**包里那个 Zig**（或源码树里 `运行环境/zig/` 那个），**链什么、
带哪些宏，是从项目里读的，不是猜的**。

#### 两个"根"，不要混

这是踩过的坑，记住它比记住别的都值：

| | 是什么 | 会不会变 |
|---|---|---|
| **包根** | 这份软件自己住在哪儿。**编译器、内核库、`项目清单.json` 都在这儿** | **永不改变** |
| **文件树根** | 文件树现在指着哪儿 | 点一下「打开文件夹…」它就变了 |

它们曾经是一个。后果：打开 `宿主/xiangqi` 去看一眼象棋源码，编译器就跟着"消失"了 ——

```
[用不了 C++] 没有编译器。找的是这一条：…\宿主\xiangqi\运行环境\zig\zig.exe
             编辑器算出来的包根是：…\宿主\xiangqi
```

现在是两个名字、两个值。**你打开哪个文件夹，都影响不到编译器。**

#### 一个文件夹就是一个程序

一个文件如果**不属于任何已知目标**（你自己新写的），那么 **它旁边的 `.cpp` 一起编**。

这条是必须的 —— `main.cpp` 一个人不是程序。`宿主/xiangqi/main.cpp` 要 `rules.cpp`、
`presenter.cpp`、`figures.cpp`、`glyph.cpp`、`computer.cpp` 才链得上；只编它自己，那些函数全
是 `undefined symbol`。

编译那行标题会报数量，**那就是判据**：

```
$ zig c++ main.cpp + 同目录 5 个          ← 它带了五个兄弟
$ zig c++ 我的游戏.cpp                     ← 单文件，就写一个
```

三条边界：

1. **不是整个项目一起编**，是同一个文件夹。子目录里的不带。
2. 清单里**有**目标时仍按目标算（开发机从 `build/` 读的时候就有；包里没有）。
3. 一个文件夹里放两个各自带 `main()` 的程序会撞，报"重复定义"—— 清楚的错误，不是静默编坏。

#### 那些"必须从项目里读"的东西从哪来

| 在哪跑 | 线索来自 | 怎么说 |
|---|---|---|
| **包里** | `项目清单.json` | 包里没有源码、没有 `build/`。清单里是"头文件在哪、带哪些宏、链哪些库、Vulkan 在哪"，**路径全部相对包根**，所以整包挪到哪台机器上都对 |
| **源码树** | `build/CMakeCache.txt` + `build/**/*.vcxproj` | 本机 CMake 的原话，开发时最准 |

两件猜错就会"链接通过然后崩"的东西：**`ZL_GPU_WITH_VULKAN`**（`PUBLIC` 宏，头文件拿它圈成员，
少了它布局不一致）和 **Vulkan 的路径**。两条路都会把它们带对。

**不重编**：源码和所有库都比 `.exe` 旧就直接跑，控制台会说"（源码和库都没变，用上次编好的）"。

**输出落在 `<包根>/build/编码器/<文件名>/`** —— 不在你打开的那个文件夹里。两个宿主都有
`main.cpp`，按文件名放会撞。

## 打包游戏

工具栏上那个「打包游戏」（`Ctrl+Shift+B`），在「运行」菜单里。它把**当前文件所在的文件夹**
打成一个能拿走的包。

**一个游戏就是一个文件夹** —— 和"一个文件夹就是一个程序"是同一条规矩，所以打包不需要另立一套
"这个游戏有哪些文件"的说法。

### 游戏是 C++ 写的

打包只有一条路：**把这个文件夹里的源文件编成一个 exe**。引擎是 C++，游戏就该是 C++ ——
工具不该猜语言，也不该有第二条会让人误会能走的路。

> 这里曾经还认过 Python，而且认得很糟：它按"你现在打开的是哪个文件"猜语言，于是在一个 C++ 游戏
> 里点开一个 `.py` 看一眼，整个游戏就改成按 Python 打；更荒唐的一次是拿 `编码器/` 自己（正好
> 十三个 `.py`）当成一个 Python 游戏去冻结。**那条路已经删掉了。**

### 两条护栏

| 护栏 | 为什么 |
|---|---|
| **不能拿工作室自己的零件当游戏** | `编码器/`、`内核/`、`引擎/`、`宿主/`、`运行环境/`…… 这些是**做游戏用的东西**，不是游戏。拿它们打包没有意义 |
| **产物不能落在游戏文件夹里面** | 打包第一步是清空输出目录 —— 落在里面就等于把游戏自己删了。（默认的 `<游戏文件夹的上一级>/发行/<名字>` 不会撞，但名字可以改，所以拦在代码里） |

两条都会在输出面板里说清原因，不是静默拒绝。

### 产物

```
<游戏文件夹的上一级>/发行/<游戏名>/
    <游戏名>.exe        游戏的代码，编成一个 exe
    依赖库/             它自己之外、跑起来要有的东西
    <数据文件>          文件夹里不是源码的东西（关卡、图片、声音），原样放在 exe 旁边
```

按下去会问一个**游戏名**（默认是文件夹名）。产物目录已经有东西时会先问要不要覆盖。

### 为什么数据放在 exe 旁边，不塞进 `依赖库/`

程序里写的是 `LoadScene("关卡.scene")` 这样的**相对路径**。把一个文件挪到子目录里，那些路径
就全断了。`依赖库/` 只放"程序之外、跑起来别的东西"。

### `依赖库/` 通常是空的，这是好事

内核是以静态库链进去的，C++ 运行库（libc++、libunwind）也是静态链的。实测一个 Zig 编出来的
exe，导入表里只有 `KERNEL32.dll` 和 `api-ms-win-crt-*`（后者是 Windows 的 API set，不是磁盘上
的文件）—— **它就是自足的**。所以一个游戏打出来真的就是一个 exe，产物目录里就那一个文件。

（`依赖库/` 这个位置留着，是给"哪天有个游戏真的要带个 DLL"用的。那时候它会有东西。）

编译的中间产物会在打包时清掉。**不是洁癖**：Zig 链 Windows 目标时一定会写一个 `.pdb`，实测一个
4.7 MB 的 exe 旁边躺着 **58 MB** 的调试库，而 `-g0` 关不掉它（试过）。报告里会写清掉了几个。

### 一件事得先说清楚

**源码树里第一次编 C++ 之前，得先把内核编出来**：编辑器要链的是 `.a`，而 `.a` 是打包脚本那一步
产出的。没有它们，编译会报一串 `unable to find dynamic system library 'zlong_system'` ——
编辑器会拦住这个，直接告诉你"内核还没编出来，跑一次 `python 打包.py`"。

（`build/` 里那些 MSVC 的 `.lib` 顶不上：ABI 不一样，Zig 链不了。）

## 画面面板

右边的面板显示"最近一次运行画出来的东西"。

### 画面怎么过来的

一根管子一个用途：

- 子进程的 **stdout = 它说的话**（print、报错）
- 子进程的 **stderr = 它显示的东西**（帧）

帧的格式（`编码器/frames.py`）故意就是 `Platform::Present` 本身的形状：

```
'ZLFR'  4 字节
宽       uint32 小端
高       uint32
pitch    uint32  每行字节数
长度      uint32  后面跟多少字节
像素     就是那么多字节的 RGBA8
```

发送端不做任何翻译，C++ 那边照写同样的字节就行。

### 帧是丢的，不是排队的

一帧 1280×720 是 3.7 MB，60 帧就是每秒 220 MB。同步写的话程序会被编辑器的读取速度拖着走。

所以两个宿主（`live.py` 和 `宿主/editor_host.h`）都是**一帧一槽 + 另一根线程往外搬**：帧循环
立刻返回，槽被占着就**顶掉旧的**。看画面的人要的是"现在是什么样"，不是"刚才每一帧长什么样"。
顶掉的记下来，程序结束时可以说出来：

```
[画面 显示 300 帧，丢掉 0 帧]
```

### 从程序自己的窗口抄一份

一个程序**不理会** `ZL_EDITOR_HOST`（比如你自己写的、或者 `宿主/viewer`），它会开自己的窗口。
编辑器照样能让画面出现在面板里：它盯着属于这个进程的顶层窗口，用 `PrintWindow` 把内容抄过来。

- 用 `PrintWindow` 而**不是**截屏，因为编辑器通常正好压在它前面 —— 截屏会截到编辑器自己。
- 这里有个 DPI 的坑：**DPI 不感知**的程序，Windows 在屏幕上把它的窗口拉大，而 `PrintWindow`
  交回来的是它**没被拉过**的像素。所以它报的尺寸**和客户区在窗口里的位置**都要除以屏幕缩放。
  不除位置的话，面板里会混进一条 Windows 标题栏。

程序保留自己的窗口 —— 那是它的键盘去的地方。这是**抄一份**，不是接管。

### 键盘

一个**用了** `ZL_EDITOR_HOST` 的程序没有窗口，所以它的键盘只能来自面板。运行开始后面板会拿到
焦点（四周出现一圈青色边框），这时按的键会以**虚拟键码**写进子进程的 stdin。

- 按住不放（自动重复）不会重复发 —— 和窗口当年的处理一致。
- 面板没在收键（比如 Python 脚本）时，键盘正常属于编辑器。
- 按"停止"会把键盘还回来。

### 鼠标

面板收鼠标的那些动作，走的是**同一根管子、同一套行协议** —— 键盘已经往下走 stdin 了，鼠标没有理由另开一条：

```
K <虚拟键码> <1 按下 / 0 抬起> [修饰键]  修饰键 1 Shift / 2 Ctrl / 4 Alt
M <x> <y>                              指针
C <1|2|4> <1 按下 / 0 抬起> <x> <y>    左 / 右 / 中，带上它发生在哪
W <格数>                               滚轮，带符号
A <R> <G> <B> <A>                      给选中的面上这个颜色，四个通道 0..1
S <路径>                               存到这个路径
L <路径>                               从这个路径读自己的模型
I <路径>                               从这个路径导入别人的网格文件
T <路径>                               给选中的面挂上这个路径的一张图（只有 BMP）
```

后三行的路径是**整行剩下的全部**，不分词 —— 路径里有空格，按空白切会把它切成两半。它们也不走键盘那条路，理由见下面「模型的存和读」。

`K` 那一行的修饰键是**后加的**（老的一行只有两个数，缺了就是 0）。它是"管子不送修饰键"那条老限制
的解 —— 有了它，**按住 Shift 拖是吸附到 0.05 的格子上**。顺带一件事：**抬起也要送**了，因为"Shift
松了"只有抬起那一下说得出来，否则吸附会卡在开着。

写的是 `编码器/main.py` 的 `_on_view_*`，认的是 `宿主/editor_host.h` 的 `consume`，两处各有一份同样的表。

**坐标是画面自己的像素，不是面板的像素。** 面板把画面缩放居中之后才画，而只有它知道缩了多少 —— 所以它先算回去再发。程序拿到 `(x, y)` 除以自己渲染的尺寸就有了一条射线，不用听人讲什么叫信箱边。落在画面外面的点**根本不发**：夹到边上会让一次滑出去的拖动看起来像沿着边框走。

**按下的位置跟着按下一起发**，不让程序去问"指针现在在哪"。两者不是一回事：一次按下和一次移动经常落在同一帧里，那时候去问指针拿到的是**移动之后**的位置 —— 拖动就少算了那一段，落点比手短一截。（这是量出来的：同一段拖动，少了这一段的落点和它自己的投影算法算出来的差 0.07 个世界单位。）落在画面外面的按下没有坐标可给，就只写前两个数、程序回落到指针 —— 但**还是要发**，否则拖出画面再松手，程序就永远以为键还按着。

**指针只留最新的，按键动作排队。** 一次拖动会产生几百个移动，只有最后一个描述"现在"，排队的话程序慢下来时鼠标会拖出一条越来越长的尾巴；而一次在两帧之间完成又结束的点击仍然是一次点击，丢掉它会让工具感觉"漏了输入"。位置是状态，按下抬起是事件。

**同一批里两队的先后是固定的：先键盘，再鼠标，再滚轮。** 同一帧里同时到达的一条键和一次点击，键一律算在前面，无论谁先写进来。一帧十几毫秒，人手做不到故意卡在中间，所以不为它另立一套带顺序的事件流；但知道有这回事，才不会指望它按写入顺序发生。

三个回调（`pointer()` / `TakeClicks()` / `TakeWheel()`）和 `TakePresses()` 摆在一起，见
[04-宿主](04-宿主.md)。不看这几个的程序一切照旧 —— 多出来的行会被 `consume` 丢掉，不是报错。

## 模板

文件 → 从模板新建：

| 模板 | 是什么 |
|---|---|
| 空脚本 | `import zlong` 加一段说明 |
| 场景脚本 | 建场景、交给机器、`SaveFrame` 写到 PNG |
| 宿主脚本 | 只讲 `Platform` 四个回调 |
| C++ 主机程序 | 上面那份骨架加上 `editor_host.h` 的接线 |

模板自己也有测试：**C++ 那份会被真的编译、链接、运行一遍** —— 模板坏了没人会发现，因为它永远
不会作为一个文件被打开。

> 顺带记一条教训：模板是**单文件**程序。验收"编辑器会不会编 C++"时只用模板，就永远测不出
> "一个程序不止一个文件"这一类 bug —— 那个 bug 只在多文件程序上露出来。**验收要两种都用。**

## 性能

（下面这组数是用一个专门跑速的旋转方块量的 —— 那个例子叫 `examples/spin_scene.cpp`，**和
`编码器/tests/` 一起从树里删掉了**。数字留着，因为结论仍然成立；要重测就得把那个例子捡回来。）

| 画面 | 谁也没看 | 编辑器在看 |
|---|---|---|
| 320×200 | 56.4 fps | 56.4 fps，丢 0 |
| 640×400 | 56.2 fps | 56.2 fps，丢 0 |
| 800×500 | 56.1 fps | 55.6 fps，丢 0 |
| 1024×640 | 42.6 fps | 渲染本身 23.5 ms/帧 |

- **编辑器跟得上**：到 800×500 为止一帧不丢。
- **丢帧只在真的跟不上时发生**。把读取端故意放慢到每次读睡 40ms：显示 7 帧、丢掉 171 帧，
  **而游戏仍然是 56.5 fps** —— 这是丢帧的全部意义。
- **56 不是 60，也不是面板的锅**：Windows 的 `sleep_for` 粒度约 15.6ms，按 16.67ms 定时就落到 56。
- **1024×640 到不了 60**，因为渲染本身要 23.5ms —— 瓶颈在引擎把帧缓冲读回来，不在面板。

（这组数讲的是引擎和面板这一层的行为，和哪个编译器无关；但它们是用 MSVC 那条链测的，
**没有用 Zig 重测过**。）
