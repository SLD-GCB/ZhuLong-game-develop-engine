# 引擎

`引擎/` 是"描述世界"的那一半。它不认识模拟器 —— 它是对着一个 `Scene` 和一个 `RenderBackend`
干活的，而那个后端可能是 Vulkan，也可能是软件光栅器，还可能是 guest 的 Maxwell。

```
scene   场景 = 数据（画面 + 声音都写在这里）
 ├── renderer   把 Scene 变成 draws
 └── sound      把 Scene 里的 emitter 变成声部
mesh    程序化网格
math    线性代数
scene_file  场景的文本形式
```

完整签名：[`参考/引擎.md`](参考/引擎.md)。

> **拿到发行包的人**：`Scene` / `Mesh` / `Math` 是这一篇里**该调**的那半边；`Renderer` 和
> `SoundRenderer` 由 `System` 拥有，不该自己 Prepare。Python 那一面只有前者，而且
> `scene_file` 整个没有。见 [08-从包里调组件](08-从包里调组件.md) 第五节。

---

## math —— `zlong::engine`

> *「一个 3D 场景需要的那么一点线性代数。全程**行主序**，因为顶点着色器的常量缓冲就是这么摆的：
> 第 i 行在字节偏移 i*16，于是 `clip[i] = dot(row_i, position)`。右手系，看向 −Z，裁剪空间深度在
> [−1, 1] —— 软件光栅器的 `1/w` 和视口映射就按这个假设写的。」*

`Vec3` / `Mat4` / `MvpBytes`，加上 `Identity` / `Translation` / `RotationX` / `RotationY` /
`RotationZ` / `Scale` / `Scale(x,y,z)` / `Perspective` / `LookAt` / `Radians`。

**坑**：角度一律用 `Radians(deg)`，不要手写小数。头文件里写着为什么：*「这里手写一个四舍五入的
字面量 —— 50 度写成 0.8727 —— 会让投影偏 4e-5，然后在近乎共面的边上把深度测试翻过来，而这
不是读那个常量的人能猜到的。」*

## mesh —— `zlong::engine`

> *「网格是生成出来的，不是加载的。**故意平面着色**：一个面的每个顶点都带那个面自己的法线，
> 所以三角形上插值出来的法线就是它，方向不变。场景的片元着色器反正会归一化它（模型矩阵会缩放
> 它）。绕序从外面看是逆时针，那是光栅器认的正面。」*

| 函数 | 出来的是什么 |
|---|---|
| `MakeBox()` | 单位立方体 `[-0.5, 0.5]³` |
| `MakeGrid(divisions, uv_tiles)` | 单位方片，XZ 平面，法线朝 +Y。`uv_tiles` 是**烘进去的**：一个 30 单位的地面要在这个参数上把砖铺好，缩放不会改 UV |
| `MakeCylinder(sides)` / `MakeCone(sides)` | 绕原点高一个单位、半径 0.5。侧面平滑着色，两个端面是平的 |
| `MakeSphere(rings, segments)` / `MakeDisc(sides)` | 直径一个单位 |
| `MakeCheckerTexture(size, cells)` / `MakeRippleNormalTexture(size, cells)` | 两张程序化贴图。没有图片加载器 |

从 Python 用同一批函数（见 [05-编码器](05-编码器.md)）。

**关键约定**：每个图元**都是一个单位大**。所以"把它放在地上"就是「先缩放，再抬高它的一半」。
`[0.5, 0.5]` 那个顶点切线帧是烘好的，不是着色时算的 —— IR 里没有 swizzle，叉乘表达不出来。

### 捏一个网格：`MeshDescription` 那扇门

上面那些是**现成的形状**。要捏自己的，入口只有一个：把一份 `MeshDescription`（**焊接**好的点、
指着它们的面、那些面穿的材质、材质采样到的贴图，再加一张硬边的表）交给 `BakeMesh`。它同时是
"手捏的"和"从文件导进来的"两条路的出口 —— 施加的规则（面朝哪边、平滑的角平均出什么、切线帧怎么
推、下标为什么是 16 位）是引擎的规则，所以只该有一份。

| 函数 | 干什么 |
|---|---|
| `BakeMesh(描述, 出网格, 原因)` | 描述 → 场景要的那份 `Mesh`。一个角一个顶点（焊缝就是这么裂开的），Newell 法线，四边面沿**较短的那条对角线**扇开 |
| `ExtrudeFace(描述, 面号, 距离, …)` | 把一个面沿它自己的法线挤出，四周补侧壁。**那个面会被换掉**（留着就是一块内部墙）。出来的面按 `[其余…, 侧壁…, 顶面]` 排，**顶面在最后** |
| `Subdivide(描述, …)` | Catmull-Clark 细分一次：每个面一个中心点、每条边一个点、每个老顶点按 `(F + 2R + (n-3)P)/n` 挪一下，每个 n 边面拆成 n 个四边面。**边界上的顶点不动** |
| `CornerCut(描述, 要切的点, 一段边长, …)` | 切角：点到的每个顶点各用一小片平面切掉。一个角一削面就可能超过四个角，所以**五个角以上的面从中心扇成三角形** |
| `DeleteFace(描述, 面号, …)` | 删掉一个面，在那儿留一个洞。**唯一一个让面变少的操作**：没人指着的点跟着丢掉、剩下的重排，硬边也跟着收 |
| `SplitByMaterial(描述)` | 按材质拆成几份（见下） |

**硬边**（`Crease`，`MeshDescription::creases`）是`Subdivide`那一条路上的一件东西：一条边在焊接的
描述里是**两个面共用出来的**，不是谁写下来的，所以"这条边是硬的"只能是一张单独的表，按 `(低,
高)` 排好序。细分的时候，硬边的边点在**它的中点**（不是那四个点的平均），于是一条硬边细分完还是
直的；一个点上连着两条硬边就沿它们走折线规则 `(6P + Q₁ + Q₂)/8`，三条以上就是个尖角、钉住。切角
的时候硬边也跟着收，不会一声不响地丢掉。

## scene —— `zlong::engine`

> *「一个场景**是什么**，作为数据。这个类型存在的意义就是场景不是代码。……它描述世界里存在的
> 一切，看得见的和听得见的：给渲染器的 mesh、material、node，给声音渲染器的 sound 和 emitter。」*

```cpp
struct Scene {
    Camera camera;                      // 听觉上的"耳朵"也是它
    Vec3 ambient;
    std::uint32_t shadow_map_size;      // 0 = 不要阴影
    std::array<float, 4> background;
    std::vector<Mesh> meshes;
    std::vector<Texture> textures;
    std::vector<Material> materials;
    std::vector<Light> lights;          // 只用前 kMaxLights 个
    std::vector<Node> nodes;
    std::vector<Clip> sounds;
    std::vector<Emitter> emitters;
    std::int32_t AddNode(mesh, material, local, parent = kNoParent);
};
```

- `Node::mesh` 是 `kNoMesh` 时，它是个纯变换组（当父节点用）。
- **父节点必须出现在子节点前面** —— `AddNode` 记的是下标。
- `Material::texture` / `normal_texture` 是 `textures` 的下标，`kNoTexture` 表示没有。
- 材质是**平铺**的：一个 material 是一个 `tint[4]` + `specular` + 两张贴图下标。

从 Python 建场景时**必须**用 `add_mesh` / `add_material` / `add_light` / `add_texture`，
不能 `scene.meshes.append(...)` —— 那是拷贝。见 [05](05-编码器.md)。

## renderer —— `zlong::engine`

> *「把 Scene 变成 draws。和 Scene 的分工是**故意**的。Scene 是数据，不知道 GPU 是什么；
> 渲染器拥有机器那一侧的一切 —— guest 内存里放上传过的网格、贴图和 per-drawable 常量的 arena，
> 渲染目标，和着色器模块。几何在 `Prepare` 里上传一次；帧与帧之间变的只有 per-drawable 常量。」*

```cpp
bool Prepare(const Scene&, width, height, GuestPa arena_base, std::uint64_t arena_bytes,
             std::string& error);
bool Render(const Scene&, std::size_t& draws, std::string& error);
const std::uint8_t* colour_pixels() const;   // RGBA8
```

**arena 是调用方给的**：`arena_base` / `arena_bytes` 是**别人**（内核的分配器）预留下来的，
不是这个类自己挑的数字。场景装不下就**拒绝**（返回 false），而不是踩过去。所以画面越大、阴影图
越大、几何越多，arena 就要越大 —— 1280×720 + 1024 阴影图大约要 64 MB。

**每帧的开销在哪**：把帧缓冲读回来。这是 Vulkan 路径的瓶颈，也是为什么 1024×640 只有 42fps。
见 [05-编码器](05-编码器.md) 的性能一节。

`Renderer::width()` / `height()` / `target_pitch()` 给出目标尺寸 —— 宿主用它们决定怎么显示。

## sound —— `zlong::engine`

> *「把场景的 emitter 变成帧。渲染器的另一半，同样的分工。渲染器走场景的节点、把可画物变成
> draws；这个走同一批节点、把 emitter 变成声部，然后把一块帧交给混音器。两者都拿相机当它们的
> 目的 —— 对声音来说它就是字面意义上的耳朵。」*

`SoundRenderer::Prepare(scene, error)` 一次，`Mix(scene, span<Frame>, error)` 每块。
等功率声像、线性衰减，听者就是 `scene.camera`。

## scene_file —— `zlong::engine`

> *「场景作为文本，于是场景是数据而不是代码。这就是 Scene 之所以是数据的**原因**：让场景长大
> 应该是编辑一个文件，而不是编辑并重编译一个 C++ 程序。」*

`ParseScene(text, out, error)` / `LoadScene(path, out, error)`。格式是一行一条指令，空白分隔，
`#` 起注释。现成例子：`宿主/scenes/demo.scene`（那份文件开头自己就是格式说明书）。

```
camera eye X Y Z            camera target X Y Z           camera up X Y Z
camera fov F                camera near F                 camera far F
background R G B [A]        ambient R G B                 shadow SIZE
light DX DY DZ  R G B                                   # 一行一个光
mesh box | mesh grid N | mesh cylinder N | mesh cone N | mesh sphere R S | mesh disc N
model 路径.model X Y Z ROTY SCALE                       # 一条指令 = 一个摆好的模型
texture checker SIZE CELLS | texture normal SIZE CELLS | texture file 路径.bmp
material R G B A [specular F] [texture INDEX] [normal INDEX] [none]
node MESH MATERIAL PARENT X Y Z ROTY_DEGREES SCALE       # PARENT −1 = 根
sound tone|noise|none ...    emitter NODE gain ... loop ...
group ...
```

图元仍然是**内建**的（box / grid / checker / tone）—— 文件格式描述不了任意网格，那是内容管道的
事，而内容管道还没有。

**`model` 是唯一一条伸到文件外面去的指令**，也是让"做出来的模型"能用上的那一条：建模器写出一个
`.model`（见下一节），`model 椅子.model 0 0 0 0 1` 把它读进来、**按材质拆开、摆好**。路径是"除了
最后五个数之外的全部"（所以它里面可以有空格），而且**相对场景文件自己** —— 所以一份场景和它引用
的模型可以整包一起挪走。

它和 `mesh` 那族不一样：那几条约好一个网格、等人自己写 `node` 去摆；这一条自己就把节点摆好了。
因为**一个模型有几种材质就是几个网格**（引擎那边一个节点一种材质），写文件的人没法知道是几个。

也正因为要相对某个目录，`ParseScene` 多了一个 `base_dir`：从文件读的时候是它的目录，写在代码里的时
候没有这么个东西 —— 那时候出现 `model` 是**报错**，不是当没看见。"文件不在"和"没人告诉我该相对
哪儿找"是两个不同的问题。

## model_file —— 一个模型存成文本

> *「一个模型存成文本，于是模型是数据，而不是一次会话。」*

`WriteModel(描述)` / `ParseModel(text, out, error)` / `LoadModel(path, out, error)` /
`SaveModel(path, 描述, error)`。和 `.scene` 同一套写法，一行一条指令，`#` 起注释：

```
mesh 4
material 0.62 0.64 0.68 1.0 0.35
material 0.90 0.20 0.20 1.0 0.30 木纹.bmp
v -0.500000 -0.500000 -0.500000
f flat   4  0   0 3 2 1   0 0   1 0   1 1   0 1
crease 0 3
```

`f` 那一行是 `<平/滑> <几个角> <材质号> <角…> <uv…>`：**"几个角"写在材质号前面**，所以后面那一
串从哪儿开始切是明确的。`material` 行是 `<颜色四个数> <高光> [贴图路径]`，**贴图在最后** —— 路径里
可以有空格，所以它一直到行尾。写几条 `material` 就有几种，**至少要有一条**（一条都没有的话读的人补
一个白的，"每个面都穿着点什么"这条得成立）。`crease <低号> <高号>` 一行一条硬边，**低号在前**；没有
硬边的文件一行也没有。所以 `mesh 3` 的老文件读得进来 —— 它只差 `crease` 这一样。

**贴图的路径是相对这个 `.model` 自己**，和场景里 `model` 那条指令同一个道理 —— 所以贴图和模型可以整
包一起挪走。也正因为要相对某个目录，`ParseModel` 才有一个 `base_dir`；没有它的时候，一条写了贴图的
`material` 是**报错**而不是当没看见。存回去的时候写的也是那条相对路径（`SaveModel` 会先拦住在内存里
造出来、没有路径可写的贴图 —— 悄悄少写一样比直接说不行坏得多）。

**逐面材质靠 `SplitByMaterial` 落地，而它不动 IR、不动渲染器。** 引擎那边一个可画节点配一种材质，
所以"一个东西上有两种颜色"在那一侧就是"两个节点"：按材质把描述拆成几份、每份只留它那些面、点按用
到的重排，然后在工具或场景那一层各加一个节点。另一条路（给顶点加一条材质索引属性）要动 Maxwell 那
条机器字的路，所以没走。

**uv 写在面上，不写在点上** —— 这不是排版方便。一个点是空间里的一个位置，几个面共用它；而 uv
说的是「这个面的这个角贴到贴图的哪儿」，同一个位置在不同的面上可以贴在不同的地方。这正是那份描述
**焊接**起来的意义，也正是 `BakeMesh` 要按角去拆的原因。把 uv 挪到点上去，就等于把焊接偷偷拆了。

**点要写在面前面**：角的下标是照着**已经读到的**点算的，所以一条 `f` 只能指着它前面出现过的点。
换来的是"第 4 行那个角是 2，前面只有 2 个点"这种能直接照着改的话。

**一个 float 写九位有效数字**（float 的保证往返数）。默认那六位不够，会让模型每存一次悄悄变一点
—— 那是过很久才会有人怀疑的事。

**路径是 UTF-8，而且中文路径只能从管子里来、不能走命令行。** 两条都是踩出来的：直接把
`std::string` 交给 `std::ifstream`，Windows 会按 ANSI 代码页解释它；而命令行更早 —— 还没进
`main` 就已经被改变了。见 `引擎/include/zlong/engine/file_io.h`，那一对函数就是为这件事存在的。

## image_file —— 读一张图片

> *「一份像素，和它从哪儿来无关。」*

`ParseBmp(bytes, out, error)` / `LoadBmp(path, out, error)`。读的是 **BMP**，因为它是这一类格式里唯一
一个"不压缩、哪儿都存得出来"的；出来就是一份 `Texture`（RGBA8 紧排、第一行在上）。

**认 24 位和 32 位、不压缩（`BI_RGB`）的那些。** 1/4/8 位的调色板、RLE、显式掩码的 `BITFIELDS`、
老式的 `BITMAPCOREHEADER` 一律拒绝并说清是哪一种 —— 一张图读成花花绿绿，比读不出来坏得多。

三件"读错了也不报错"的，每一件都造了一份出来对像素：

| | |
|---|---|
| **行序** | 文件里第一行在**最后**，除非高度写成了负数。两种都要认，而它们印出来一样 —— 搞反了只会上下颠倒，不会报错 |
| **行对齐** | 每行按 4 字节补齐，宽度是奇数时行尾有填充。不跳过它，图会**斜着扭曲** |
| **32 位的第四个字节** | 按标准是"保留"，可一半的工具拿它当 alpha、另一半一律写 0。**全 0 当作不透明**，否则每一张 32 位的图都是透明的 |

（PNG 没做，因为它要一个 inflate；那是一段不该顺手写的代码。）

## obj_file —— 读别人的网格文件

> *「导入不是第二条路，是另一个生产者。」*

`ParseObj(text, out, 报告, error)` / `LoadObj(path, out, 报告, error)`。读的是 **Wavefront OBJ**，
因为它是这一类文件里唯一一个"文本、几乎没有语法、哪儿都导得出来"的。读进来之后它就和其他任何一个
模型一样了 —— 同一个类型、同一个烘、同一套编辑操作。

认这些：

```
v x y z                     点
vt u v                      uv
vn x y z                    法线（读，但不用）
f  a  b  c                  面；角可以写成 a、a/b、a//c、a/b/c，下标从 1 数，可以是负的
s off | s 1                 这一片是不是平滑的
o / g / usemtl / mtllib     认得出，但只跳过
#                           注释
```

**它和这份表示是天生一对**：OBJ 本来就不焊（点是点、uv 是 uv，一个角是一对下标），而 `MeshDescription`
正好也是"焊好的点 + 每个角自己的 uv"。所以这里没有"按缝拆点"这一步。

**三条有损的，都报在 `ImportReport` 里**（改过别人的文件就得说清楚改了什么）：

| 文件里 | 进来之后 |
|---|---|
| 五个角以上的面 | 从第一个角**扇成三角形**（凹陷的多边形会切出细长的三角形，这是已知的代价） |
| 没被任何面用到的点 | **丢掉**。留着不叫忠实，叫留了一群看不见却点得到的点 —— 顶点拾取是按屏幕距离找的 |
| `vn` 法线 | **不用**。这个引擎的法线是烘出来的，顶点上没有地方塞它；"平还是滑"按 `s` 判断，没有 `s` 就一律平（拿 `vn` 去倒推是猜） |

**材质不在这份东西里**：`usemtl` 跳过的原因不是省事 —— 一个模型的材质是它被摆进某个场景之后那一步
的事（`Scene::materials` + `Node`），塞进网格里会有第二个说法。

不认识的指令**跳过并记一笔**，不拒绝整个文件：别人的导出器多写一行，不该让整份文件读不进来。
