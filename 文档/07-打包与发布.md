# 打包与发布

> **这一篇讲的是"把烛龙自己装成一个能拿走的包"。**
> 把**用烛龙写的游戏**装成包是另一件事 —— 编辑器里那个「打包游戏」按钮，见
> [05-编码器](05-编码器.md) 的打包一节。两者用同一套想法（代码进 exe、依赖进 `依赖库/`），
> 但一个装的是工具，一个装的是作品。

```bat
python 打包.py                  :: 装到 发行\烛龙-<日期>\
python 打包.py --zip            :: 顺便压成 zip
python 打包.py --into D:\某处    :: 换个地方装
python 打包.py --name 烛龙-试装   :: 换一个目录名
python 打包.py --no-cxx         :: 不编 C++ 内核（快，调包的时候用）
python 打包.py --no-python      :: 不带 Python 运行环境
python 打包.py --no-exe         :: 不冻 exe
```

实测：**754 MB，压完 193 MB，约 70 秒**（C++ 内核没变的时候）。

## 一、包是什么形状

```
烛龙.exe                  1.9 MB   所有 Python 代码，冻成一个。双击它就是全部
建模器/建模器.exe         5.1 MB   编辑器「3D 建模」那一页起的工具。**成品，不是源码**
依赖库/                    81 MB   上面那个 exe 的依赖：PySide6、python313.dll、Qt 插件……
运行环境/
    zig/                  321 MB   C++ 编译器（Zig 0.13）—— 编用户写的 .cpp 用它
    ziglib/
        zlong.dll           5.3 MB  **整个 C++ 后端，一个二进制**（1434 条导出）
        libzlong.dll.a             链它用的导入库
    python/               100 MB   跑用户写的 .py 的解释器
        harness/                   子进程的宿主程序（live.pyc + frames.pyc，字节码）
    vulkan/
        include/           36 MB    Vulkan 的头
        lib/                        Vulkan 的导入库
include/                  149 MB   **接口**：16230 个头（我们自家的 85 个只留类型和签名）
工具链/                            让编译器编得动这个内核的垫片
项目清单.json                      编辑器编 C++ 需要知道的一切
文档/                              这份文档
```

**两个 exe 都带着图标**（项目根目录那张 `烛龙.jpg`）—— `烛龙.exe` 是 PyInstaller 的 `--icon` 嵌的，
`建模器/建模器.exe` 是 CMake 里一条资源规则嵌的（见下）。**窗口标题栏上那个**另有一份：`依赖库/`
底下的 `icon.ico`，由 `main.py` 在启动时设给 Qt —— 不设的话标题栏是 Qt 的默认图标，和任务栏对
不上。

### 图标是生的，不是手工转的

**源图只有 `烛龙.jpg` 一张，两个 `.ico` 都是它生出来的。** `打包.py` 的 `build_icons` 在开工第一
步做这件事：裁成正方形、缩成 7 个尺寸（256/128/64/48/32/24/16）、写成 `.ico`。换了图重跑一次打包
就够。

那两个 `.ico`（`编码器/icon.ico`、`宿主/modeler/icon.ico`）**也留在源码树里** —— 编 C++ 那一步
要用后面那个，而 `cmake --build build` 是打包脚本之外也会跑的。已经在树里、又比源图新，
`build_icons` 就不动它。Pillow 不在就跳过，接着用旧的那一份：**不能因为少一个画图库就整包打不出来**。

### exe 的图标是"资源"，不是"旁边的图"

Windows 的 exe 图标是一个**资源**，要 `.rc` 编出来的 `.res` 才进得去。两条路：

| 哪一套 | 怎么嵌 |
|---|---|
| **Zig**（打包和 `build-zig`） | 它自带一个资源编译器（`zig rc`），编出来的 `.res` **直接交给链接器** —— 实测 `zig c++ foo.o icon.res -o foo.exe` 资源就进去了。`CMAKE_RC_COMPILER` 那套（CMake 默认会去找 `windres`，而它不在包里）一个字都不用碰 |
| **MSVC**（开发时的 `build/`） | 它自己有 `rc.exe`，`.rc` 当普通源文件加进去就行 |

两套都不是就什么都不做 —— **没有图标是一个少了图标的东西，不是一个编不出来的东西**。

实测：**673 MB，约 150 秒**；C++ 那一半没变的话 40 秒。

**包里没有一个 `.cpp`。** 没有 `CMakeLists.txt`、没有 `.vcxproj`、没有 `build/`、没有测试、
没有 `.bat`，产品目录里也没有 `.py`（运行环境里那些是**字节码**）。

**两个例外是 `烛龙.exe` 和 `建模器/`，而且是有意的。** 它们不是"用户写的程序"，是这份软件自带的
东西：包里没有它们的源码、也没有谁会去编它们。发的是成品。

## 一之二、C++ 那一半：一个 DLL，和只剩签名的头

**整个后端是一个 `zlong.dll`** —— 内核八个子系统 + 引擎 + 宿主音频 + 第三方（dynarmic / fmt /
mcl / Zydis / Zycore），全部收进去。从前是十五个 `.a` 摊在 `ziglib/` 里，现在是一个二进制。

### 头里的实现被挖走了

我们自己的 85 个头，铺进 `include/` 之前要过一遍刀（`打包.py` 的 `strip_bodies`）：**函数体挖掉、
成员初始化列表挖掉、带花括号的常量初值换成 `extern` 声明**。一共切掉 **369 处实现**。

| 头 | 变化 |
|---|---|
| `engine/mesh.h` | 1611 行 → **406 行**（`BakeMesh` / `CornerCut` / `Subdivide` 只剩签名） |
| `ram/registers.h` | 99 行 → 66 行 |
| `cpu/host.h` | 只剩一张虚函数表（连默认实现的 `{}` 都挖掉了，只剩 `;`） |

**挖掉的东西得有地方去** —— 它们已经编进 `zlong.dll` 了。但 `inline` 的函数"没人用就不发射"，
所以打包时会**给每一个函数声明挂一句 `__attribute__((used))`** 再编一遍，把它们全钉出来
（`pin_functions`，实测 **367 个函数**）。

> **两半必须一样多。** 头里挖掉几处，库里就得钉几处 —— 用的是**同一个扫描**（`_functions`），
> 所以不会对不上。
>
> 这一条踩过坑：早先只钉"带 `inline` 关键字"的那些，而**写在类里面的成员函数是隐式 inline，
> 根本没有那个关键字**，于是 `Camera::View()` / `Node::Drawable()` / `System::ok()` 这一大批
> 头里只剩声明、库里没有符号 —— 用户一编就是一片 `undefined symbol`。

### 有一类绕不开：模板和常量

**2 处模板函数**的体留在了头里（`service/handle.h` 的 `GetAs`、`service/object.h` 的 `is`，各
3 行）。**C++ 规定模板的定义必须在头里** —— 用户实例化它的时候要看得到，挖走就编不出用户的程序。

`constexpr` **常量**同理（`kMaxLights`、`kDescriptorAfBit` 那些）：它们是常量，编译期就要用
（数组大小、`static_assert`）。

报告里每次都点名：

```
include/  16230 个头、149 MB —— 接口（自家 85 个切掉了 369 处实现；第三方那些原样）
  2 处模板函数的体留着 —— C++ 规定它必须在头里（实例化的时候要看得到定义），这是唯一绕不开的一类
  切过的头编了一遍：64 个全过
```

### 怎么验的

切的是**文本**，所以"看着对"没有任何意义。铺完之后有两道：

1. **拿包里那份切过的头一个一个编**（`verify_headers`）—— 切坏一个大括号当场就红。
2. **另一套"笨"办法再扫一遍**（`leftover_bodies`）：一行里有 `{`、`{` 前面有 `)`、又不是
   `if` / `for` / `while` 那种控制语句 —— 就算数。

> 第 2 条为什么非要有：**切和查要是同一套逻辑，切漏了查也漏。** 上一版就是拿 `strip_bodies` 去查
> `strip_bodies`，结果 `ram/registers.h` 那 17 个函数体一路漏到了成品里，而检查一声没吭。

## 二、四件归一了的事

### 一、代码进 exe，依赖进依赖库

`编码器/` 里十二个 `.py` 互相 `import`，以 `main.py` 为入口冻成一个 exe。用 PyInstaller 的
**onedir** 而不是 onefile：onefile 每次启动都先把自己解到一个临时目录再跑，Qt 那么大的一坨解一遍
要几秒 —— 一个每次开都要等几秒的编辑器不是编辑器。

依赖不塞进 exe 里，它们躺在旁边的 `依赖库/`（`--contents-directory`）。那是给人看的，也少挨一点
杀毒软件的误判。

**没有启动脚本。** 不叫 `启动.bat`、不叫 `launch.py`，双击 `烛龙.exe` 就是全部。那两个文件是
"编辑器还是十几个 .py、得先找一个解释器"时代的遗留；现在 exe 自带 PySide6，自己就是那台机器。
（顺带：它们的存在一直是"自带运行环境必须叫 `runtime/` 这种 ASCII 名字"的唯一理由。）

### 二、两套解释器就是软件的运行和编写环境

* `运行环境/python/` 跑用户写的 `.py`
* `运行环境/zig/` 编用户写的 `.cpp`，链的是 `运行环境/ziglib/` 里那个内核

**为什么是 Zig 而不是 MSVC**：微软的编译器不允许随包再分发，Zig 允许（MIT）。而 Zig 一个二进制
里就有 clang 前端 + lld 链接器 + mingw-w64 的头和库 + libc++，一整套。

**版本钉在 0.13**（clang 18）。0.16（clang 21）收紧了一条模板模板参数的匹配规则，`dynarmic`
自带的 `mcl` 编不过 —— 试过，不是猜的。

### 三、软件不碰系统环境

这说的不是"尽量不碰"，是三条硬规矩：

* **编译器只有一个** —— `运行环境/zig/zig.exe`。不去 PATH 上找，也没有备胎。一个会回退到"这台
  机器碰巧装了什么"的编辑器，是一个行为取决于机器的编辑器。
* **解释器只有一个** —— `运行环境/python/python.exe`。跑用户脚本时，机器上设的 `PYTHONPATH`、
  `PYTHONHOME` 一律丢掉，不让别人的安装方式渗进来。
* **包里的编辑器不认识 `build/`**。它编 C++ 要知道的那些事 —— 带哪些宏、链哪些库、头在哪 ——
  打包时写进 `项目清单.json`，里面的路径全是**相对包根**的。

  老办法是把开发机的 `build/`（`CMakeCache.txt` + 86 个 `.vcxproj` + 93 MB MSVC `.lib`）搬进包。
  那些路径全是"某台机器上的绝对路径"，而且 **Zig 根本链不了 MSVC 的目标文件** —— 搬进包就是死
  重量。现在包里一件 MSVC 产物都没有。

### 四、发接口，不发实现

内核、宿主、引擎的 `.cpp` **一个都不进包**。它们的实现只以库的形式存在（`ziglib/` 那 15 个
`.a`），包里留下的是接口（`include/`）。

用户写代码时 `#include` 的是头、链的是内核 —— 在引擎**之上**写东西，而不是在读引擎的实现。
这也是一个 SDK 该有的样子。

**所有头拍平到一个 `include/`**。这是安全的，因为每个部分自己 `include/` 底下的命名本来就不
重叠：八个子系统分别是 `zlong/gpu/…`、`zlong/ram/…`，boost / dynarmic / vulkan 也各自以自己的
名字开头。**实测 15898 个头，0 处冲突。** 拍平之后编译器只要一条 `-Iinclude`。

## 三、`项目清单.json`

编辑器编 C++ 要知道的一切，就这一个文件：

```json
{
 "格式": 1,
 "包含": ["include", "运行环境/vulkan/include"],
 "定义": ["NDEBUG", "ZL_GPU_WITH_VULKAN=1"],
 "库": ["zlong_system", "zlong_engine", "dynarmic", "vulkan-1", "user32", ...],
 "vulkan": "运行环境/vulkan/lib/vulkan-1.lib",
 "目标": []
}
```

几条要记住的：

* **路径全部相对包根。** 所以整包挪到哪台机器上都对。这是它取代 `build/` 的全部意义。
* **`定义` 必须原样带上。** `ZL_GPU_WITH_VULKAN` 是 `PUBLIC` 宏，头文件拿它圈**成员**；少了它，
  用户那边编出来的 `System` 和库里那份布局不一样，**链接通过、第一次调用就崩**。
* **`库` 里是裸名字**，不带路径也不带 `.lib`。但**不是**配一条 `-L运行环境/ziglib` 就完事 ——
  `ziglib/` 保留的是源码树的目录形状（`内核/RAM/`、`引擎/`、`external/dynarmic/…`），所以每个库
  配的是**它自己那一层**的 `-L`（`cpp.py` 的 `link_arguments` 一个库发一对）。配错的症状是
  `unable to find dynamic system library 'zlong_gpu'`，听起来像编译器坏了。见
  [08-从包里调组件](08-从包里调组件.md) 第二节。
* **`目标` 是空的**，因为包里没有源码，没有任何文件会是"某个程序的源文件"。底下"一个文件夹就是
  一个程序"那条补上了它原来承担的那件事。

## 四、编辑器在包里怎么编 C++

**一个不属于任何目标的文件，按文件夹算一个程序**：它旁边的 `.cpp` 一起编。

这条是必须的 —— `main.cpp` 一个人不是程序。`宿主/xiangqi/main.cpp` 要 `rules.cpp`、
`presenter.cpp`、`figures.cpp`、`glyph.cpp`、`computer.cpp` 才链得上；只编它自己，那些函数全
是 `undefined symbol`。

编译那行标题会报数量，**那就是判据**：

```
$ zig c++ main.cpp + 同目录 5 个
$ zig c++ 我的游戏.cpp                      ← 单文件，就写一个
```

三条边界：

1. **不是整个项目一起编**，是同一个文件夹。
2. 清单里**有**目标时仍按目标算（开发机从 `build/` 读的时候就有；包里没有）。
3. 一个文件夹里放两个各自带 `main()` 的程序会撞，报"重复定义"—— 清楚的错误，不是静默编坏。

## 五、验收：怎么算打包通过

**从包里真的启动一次，两种运行都做一遍。** 只在原目录里 `python 打包.py` 成功，什么都不算。

清单（都是实测过的）：

```
烛龙.exe 启动                窗口「烛龙 编码器」1550×830
包内路径                    sys.executable 在包根，project_root() = 包根
解释器                      project_root()/运行环境/python/python.exe
编译器                      Toolchain.find → 包内 运行环境/zig/zig.exe
zlong 模块                  包里那个是 Zig 编的；导入表里**没有** MSVCP140 / VCRUNTIME140
项目清单                    2 个头文件目录、2 个宏、26 个库、0 个目标
用户新建 .cpp               退出码 0 → 跑起来 backend: vulkan / frames=3 draws=4 faults=0
用户新建 .py                经 harness/live.py 回来 3 帧 1280×720，退出码 0
现有目标的程序              （包不带宿主源码，这条只在开发机上做）
双击 exe                    （没有启动脚本，这是唯一的入口）
```

**验收要用一个"多文件的程序"**，不能只用编辑器自带的模板 —— 模板是单文件的，而"只编一个文件"
这个 bug 恰恰只在多文件程序上露出来。这条是踩过的，见下面"有意留下的空缺"。

## 六、有意留下的空缺

写文档的人有责任说清楚哪里还没做完，否则读的人会以为是自己的错。

| 空缺 | 说明 |
|---|---|
| **打包机上仍然要有一份 `build/`** | `打包.py` 从它读 Vulkan 的路径和"库都叫什么名字"（`.vcxproj` 和 `Release/*.lib`）。用户那边一点不碰，但**出包这台机器要先跑过一次 Visual Studio 的构建**。要彻底去掉，得改成从 `build-zig/` 的 `.a` 里取名字 |
| **打包装不进一份正在运行的包** | `打包.py` 是"先清空目标目录、再往里装"。旧的那份一开着（它的 `qwindows.dll` 会被加载），`clear()` 就失败；中途失败还会留下半个包。正解是装到 `发行/<名字>.装到一半/` 再整体改名换过去 |
| **中间目录是写死的名字** | `build-打包/`（PyInstaller）和 `build-zig/`（CMake/Ninja）不跟目标名绑。**两次打包同时跑必然互踩**，症状是 `base_library.zip 找不到` 和 `ninja: failed recompaction` |
| **没有锁** | 第二个 `打包.py` 跑起来不会拒绝，直接开干 |
| **TLS 之外的 Qt 插件是手工列的单子** | `_EXE_DROP` 每一条都在一份真 exe 上删掉、启动、看窗口出不出来验过，但它是"跟着文件名字走"的，PySide6 换版本要重新验一遍 |
| **Zig 编译器 307 MB** | 是包里最大的一块。`lib/include` 里是整个 mingw-w64 和 libc++ 的头，剪不得。第一次链接还会现场编一遍它自己的 libunwind，会吐一片 `dllexport` 警告 —— 之后进缓存就不出声了 |
| **`编码器/tests/` 现在是红的** | 见 [06-测试](06-测试.md) |
