# 内核

`内核/` 是模拟器那一半。八个模块，从下到上：

```
service  内核/HLE：系统调用、对象、线程、地址空间、各服务
mount    挂载表：名字 → 只读树
audio    混音：把声部求和成帧
gpu      Maxwell 3D：渲染进 guest 的显存
cpu      四个 Cortex-A57
SSD      块设备
RAM      内存 + MMU
system   机器：拥有以上全部并驱动 —— 见 03/05
```

每一层的完整签名在 [`参考/`](参考/)。这一篇讲**职责和怎么用**。

> **拿到发行包的人**：这八层在包里都以库的形式存在（`运行环境/ziglib/`），头也都在 —— 但一个
> 宿主程序**只用 `zlong::system`**，下面这些是机器的内政。从包里看它们各自的头、库、该不该调，
> 见 [08-从包里调组件](08-从包里调组件.md) 第六节。

`内核/system` 是顶层，见 [README 的形状图](README.md)。一个宿主程序**只用** `zlong::system`，
不用它下面任何一层 —— 例外是你在写测试，或者你在扩展内核本身。

---

## RAM —— `zlong::ram`

> 源码里的话：*「guest 物理内存加上一个真的 MMU，通过 `cpu::GuestMemory` 这个总线暴露给 CPU 层。
> 到这里来的地址是 guest 的**虚拟**地址（dynarmic 不做翻译）。四个核碰的每一样东西都经过这个
> 对象。」*

| 类型 | 是什么 |
|---|---|
| `Ram` | 顶层对象。实现 `cpu::GuestMemory`，所以 CPU 层只看见一个内存总线 |
| `PhysicalMemory` | 真正的字节。**一个**，所有人共用 |
| `Mmu` / `AddressSpace` / `Descriptor` | 页表翻译。`TranslateResult` 说明为什么翻不过去 |
| `PhysicalRegion` / `RegionKind` | 物理地址的用途划分 |
| `SystemRegisters` | 特权级（EL0/EL1…），内核进入异常级时告诉它 |

**怎么用**：构造 `Ram(dram_bytes)`，把它交给 `cpu::Cpu` 当 `GuestMemory`，也交给 `gpu::Gpu`。
`PhysicalMemory::allocate(n)` 是**唯一**的分配器 —— 渲染器的 arena、翻译表、模块镜像全都从这个
同一本账上出。这就是为什么"两个分配器撞在一起"这种 bug 在这里不可能发生。

**坑**：地址到这里是虚拟地址。你要是拿一个物理地址去读，它会按页表翻一遍，翻到别处或者失败。

## SSD —— `zlong::ssd`

> *「字节可寻址的块设备。上面的一切（容器解析、文件系统、面向 guest 的存储设备）都对着一个
> `BlockDevice` 说话，所以同一套代码既能服务一个宿主文件，也能服务模拟出来的 SD 卡。」*

`MemoryBlockDevice`（内存里的一块）和 `FileBlockDevice`（宿主上的一个文件）。`Container` 解析
XCI/NSP 那类容器，`Partition` + `PartitionInfo` 是里面的分区。

**怎么用**：`FileBlockDevice(path, offset, size)` 包住宿主的镜像文件，交给 `Container::Open`，
拿到 `Partition`，再交给 `mount`。

---

## cpu —— `zlong::cpu`

> *「四个 Cortex-A57，它们**协作**。四个核跑在四根宿主线程上（真并行）。让它们协作而不是仅仅
> 共存的是：一个共享的 `Dynarmic::ExclusiveMonitor(4)` 加每个核自己的 processor_id，于是
> LDXR/STXR 是真的跨核原子序列；一个共享的 `GuestMemory`，所以一个核写的东西另一个核立刻看得见
> （没有模拟的缓存）。」*

| 类型 | 是什么 |
|---|---|
| `Cpu` | 四个核。`CpuHost` 是它回调出来的接口 —— 内核实现它 |
| `Core` / `Arm64Interface` | 单个核。`WaitKind` 说明它在等什么 |
| `GuestMemory` | 内存总线接口（由 `ram::Ram` 实现） |
| `SvcCall` / `FaultInfo` / `MemoryFault` | 往外报的事件 |
| `CodeWriteObserver` | 有人的写碰到了可执行内存 → 所有核对该范围的翻译作废 |

**怎么用**：实现 `CpuHost`（`OnSvc` / `OnInterrupt` / `OnMemoryFault` …），构造 `Cpu(memory, host)`，
`Start()`。**CPU 层不含系统调用号、不含 HLE、不含 guest 异常模型** —— 它只报告事件，由
`service::Kernel` 决定那是什么意思。

---

## gpu —— `zlong::gpu`

> *「渲染进 guest 自己显存里的帧缓冲：这里**故意**没有窗口、没有交换链、没有呈现。显示是另一件
> 事，是后面的事。」*

| 类型 | 是什么 |
|---|---|
| `Gpu` | 设备。`SubmitPushbuffer` 是入口；`GpuHost` 回调内核 |
| `Maxwell3D` / `PushBufferReader` / `Method` | 方法流解码 |
| `Channel` / `Job` / `SubmitResult` | 通道与提交 |
| `GpuAddressSpace` / `GpuMemoryManager` / `Mapping` | GPU 自己的地址空间与 nvmap |
| `RenderBackend` / `RenderTarget` / `VertexAttribute` | 两个后端（Vulkan / 软件）共同遵守的接口 |
| `shader::` | Maxwell 解码 → IR → 解释器 / SPIR-V |
| `GpuFault` / `GpuFaultKind` | 出错时报什么 |

两个后端：`vulkan::VulkanBackend` 和 `software::SoftwareBackend`。后者永远可用，是正确性兜底；
前者是拿来玩的。`RenderBackend` 的接口就是两者的共同点。

**怎么用**（内核侧）：`gpu.attach(host)`，然后 guest 的一次提交就是 `SubmitPushbuffer(...)`。
Gpu 从不主动打断谁 —— 它通过 `GpuHost` 说"我要一个核打盹"或者"给我一个中断"。

**坑**：`ZL_GPU_WITH_VULKAN` 会改头文件里的类布局，见 [01-构建](01-构建.md)。

## audio —— `zlong::audio`

> *「把声部求和成帧。它对渲染路径而言相当于软件光栅器：把描述变成采样本身的那一环。声部按
> clip 自己的采样率读 clip，写进混音器输出采样率的帧里 —— 所以重采样的活在这里，上面谁都不用
> 知道。」*

| 类型 | 是什么 |
|---|---|
| `Clip` | 一段采样 |
| `Voice` | 一个正在响的声部 |
| `Sink` | 输出端接口。`WavSink` 写文件，`宿主/audio_device` 是声卡 |
| `Mixer` | 把它们加起来 |

**怎么用**：实现 `Sink`（一个 `Submit(span<Frame>)` + 一个 `Finish()`），交给 `System::set_audio`，
然后 `System::Mix(seconds)` 按块喂它。

---

## mount —— `zlong::mount`

> *「挂载表：名字 → 只读树。挂上的源按 `<名字>/<树内路径>` 寻址。挂载名是一段，所以一条路径的
> 第一段选树、剩下的在树里解析。表拥有树，每棵树让它的后备设备活着。」*

| 类型 | 是什么 |
|---|---|
| `MountTable` | 名字 → 树。`Resolved` 是查到的结果，`Lookup` 说明为什么没查到 |
| `ReadOnlyTree` / `Node` | 一棵树。`HostFileDevice` 让它落在宿主文件系统上 |
| `Archive` / `ArchiveEntry` / `ArchiveLayout` | 归档格式 |
| `PartitionReader` / `FlatArchivePartition` / `OpaquePartition` | 分区里的读取器 |
| `SystemEnvironment` | 模拟出来的系统目录（`/system`、`/savedata` …） |

**怎么用**：`table.Mount("sdmc", tree)`，之后 guest 的 `"sdmc:/foo/bar"` 就能解析。
`MountError` 是显式的 —— *「挂载名写错」和「没有这个挂载」是两个不同的问题，`"它没work"` 不是
诊断。」*

---

## service —— `zlong::service`

> *「内核：CPU 层回调进来的那个 `CpuHost`。CPU 层不含系统调用号、不含 HLE、不含 guest 异常模型：
> 它报告事件，由这里决定那是什么意思。`OnSvc` 是正门，`OnInterrupt` 是另一扇，它对"没做完"
> 这件事是诚实的：guest 异常入口没实现，所以中断到不了 guest。这个缺口是被**计数**的，不是被
> 藏起来的。」*

| 类型 | 是什么 |
|---|---|
| `Kernel` | 内核。`OnSvc` / `OnInterrupt` / `attach_gpu` / `attach_audio` |
| `KProcess` / `KThread` / `KObject` / `KAddressSpace` | 内核对象 |
| `HandleTable` / `Slot` / `ObjectKind` | 句柄 |
| `IpcBuffer` / `IpcRequest` / `IpcResponse` / `Session` | IPC |
| `BootConfig` / `BootedProcess` / `ModuleImage` | 启动 |
| `services::` | 各服务：`nvdrv`（GPU）、`fsp`（文件）、`time`、`audout`/`audren`（音频）、`debug` |
| `SyncObject` | 同步原语 |

**怎么用**：`Kernel kernel(ram)`；`kernel.attach_gpu(gpu)`；`kernel.attach_audio(sink)`；
`kernel.Boot(BootConfig{...})`。之后核心里跑的东西通过 `OnSvc` 进来。
`内核/system::System` 已经把这些连好了 —— 除非你在写内核测试，否则不用自己接。

**没做完的**：guest 异常入口。中断被记下来但送不进 guest。

---

## system —— `zlong::system`

见 [README 的形状图](README.md) 和 [03-引擎](03-引擎.md)。一句话：**它是那台机器**，拥有
`ram` / `gpu` / 后端 / `service::Kernel` / `engine::Renderer` / `SoundRenderer`，并且驱动循环。
宿主只实现 `Platform`（四个方法：`Pump` / `Present` / `OnFrame` / `OnMix`）。

完整签名和逐条注释：[`参考/内核-system.md`](参考/内核-system.md)。
